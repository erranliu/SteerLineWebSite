**SteerLine 是一个以 Roadmap 驱动、深度参与项目流程的 AI 开发系统，同时提供开发方法与配套工具。**

它建立在多 Agent 编排能力之上，将规划、文档、执行、验证和交付连接起来。项目的推进有明确的目标与任务依据，执行产生的结果也能回到规划中，为下一轮开发提供依据。

**开源项目，尚未发布。** 下文介绍完整产品方向与目标工作方式；当前能力与后续方向见文末「当前阶段」。

<a id="workflow"></a>

## 一个项目怎样持续推进

以「增加一个依赖公共接口的新功能」为例，目标流程会把规划、实现与验收放在同一条工作链上：

1. **确定阶段成果。** 用户明确功能目标、优先级和关键取舍，Roadmap 将目标拆成公共接口、使用接口的功能，以及可以独立准备的测试工作。
2. **明确任务依据。** Spec 描述成果、范围与通过条件；Plan 安排实现步骤、验证方式和必要环境。任务交接需要哪些内容，在开工前明确。
3. **按依赖组织执行。** 使用接口的任务等待接口交付；边界独立的测试准备可以并行进行。任务正式进入 DAG 后，执行范围与依赖被固定。
4. **实现、测试与修复。** 执行 Agent 依据任务文档开展开发，记录结果与问题。需求发生变化时，核对受影响的任务、规格与成果，再继续推进。
5. **核验交付，继续规划。** 审查代码、测试与必要的人工验收，核验真实 PR 合并等交付事实。满足依赖后释放后续任务，将实际结果和待决策事项带回 Roadmap。

这个闭环连接了「准备做什么」与「实际交付了什么」。当前阶段，Roadmap 的后续调整仍需要人受控推进；面向用户的主 Agent 与完整周期管理属于后续方向。

<a id="roadmap"></a>

## Roadmap 与任务 DAG

Roadmap 管理阶段成果与整体推进，任务 DAG（有向无环依赖图）表达任务之间的前置关系。Spec 定义单项任务的成果，Plan 安排如何实现与验证。

拆分任务时，先明确独立成果和交接边界。比如公共接口任务需要交付接口约定、实现与验证结果，消费接口的任务据此判断是否具备开工条件。合理并行来自这些清晰的边界。

草稿用于讨论目标和备选方案；正式任务承载已经确认的执行范围。启动时固定相关依据，执行中出现需求变化时评估其影响，交付结果再支持下一轮规划。

<a id="acceptance"></a>

## 测试与验收从规划开始

任务在规划时就要回答「怎样算通过」。Spec 定义通过条件，Plan 安排验证方式，任务专属验收记录保存实际行为、结果与证据。缺少测试环境或必要能力时，应在规划和执行安排中明确。

测试按目的分层：最小代码检查、核心流程冒烟、可独立并行的功能测试，以及临界情况等可复用测试各有职责。项目通过可读说明和结构化清单，记录入口、环境和适用范围，按变更影响选择需要执行的验证。

测试判断某个版本的行为是否符合预期，验收还要判断任务承诺的成果是否成立。可自动完成的部分纳入执行计划；体验和产品取舍等人工事项，记录参与安排、待验状态与实际阻塞范围。允许后置的人工项保留待验标记，关键前置与真实失败继续阻塞相关推进。

通过、失败、跳过和未验分别记录，结果关联具体版本、执行范围和证据。编译成功、代码生成与 PR 创建是过程事实，任务完成仍需要对应的验证和交付依据。

<a id="documents"></a>

## 分层文档，让开发依据持续有效

文档承担不同职责，通过引用连接，Agent 可以据此找到当前工作需要的规则、计划与实际结果。

| 层次 | 回答的问题 | 主要内容 |
| --- | --- | --- |
| 通用规范 | 应遵循哪些共同要求？ | SteerLine 提供的项目规范、Spec/Plan 规则和测试架构规范 |
| 项目约定与长期文档 | 本项目怎样落实要求，当前怎样工作？ | 技术栈、环境、项目流程、测试指南、长期设计和架构 |
| 规划与任务文档 | 本轮做什么，怎样实施和验证？ | Roadmap、Spec、Plan 与任务专属验收安排 |
| 结果与证据 | 某个版本实际做到了什么？ | 测试报告、验收结果、交付记录与原始证据定位 |

通用规范由 SteerLine 统一提供，项目维护自己的落实方式。任务执行时固定相关版本；结果产生后更新记录；影响长期行为的变更同步维护设计与规范，让计划、实现现状和历史证据各有清楚的位置。

<a id="collaboration"></a>

## 用户与 Agent 怎样协作

**目标工作方式：由 SteerLine 主 Agent 承担主要用户交互与项目流程管理。** 用户与它讨论需求、审阅规划和了解结果，接入的执行 Agent 依据明确的任务文档开展具体开发。

| 参与者 | 职责 |
| --- | --- |
| 用户 | 决定产品目标、优先级、关键取舍与授权范围，参与必要的人工验收和交付决策 |
| SteerLine Agent 与系统 | 澄清需求，组织 Roadmap 和任务文档，维护依赖与流程要求，监督执行并汇总待决策事项 |
| 执行 Agent | 在 Spec 和 Plan 明确后，完成实现、测试、修复、提交和 PR 等具体工作 |

Agent 负责理解需求、提出方案和处理复杂工作，工具检查任务材料、依赖条件、执行资格与交付事实。需要用户决定或超出授权的事项回到用户，后续工作依据明确的决定继续。

产品方向允许用户已有的 Codex、Claude 等 Agent 作为执行器参与。**当前已接入的路径是本地 Codex、本机 Orca 和远端 Orca；Claude 接入不能视为当前已实现能力。**

<a id="current-stage"></a>

## 当前阶段与后续方向

截至 2026 年 11 月 1 日，项目 README 记录了以下基础。各项能力的实际已验范围由固定版本、运行环境和专属验收记录决定。

| 范围 | 当前基础 | 边界与下一步 |
| --- | --- | --- |
| 任务与执行 | 任务 DAG、依赖检查、独立执行候选、会话反馈与真实 PR 合并核验；核验后释放满足条件的后继任务 | 具体执行资格和验收范围按所选执行方案判断 |
| Roadmap 转正 | Markdown 读取解析、任务关系确认、Spec/Plan/验收文档生成、文档发布和正式入图；真实 Runner、浏览器与 GitHub 文档 PR 主链已有验证 | 人工体验等未验范围继续按专属验收记录跟踪 |
| 开发规范与测试 | 通用项目规范、分级测试、结构化清单、验收记录和按提交保存的测试历史 | 完整流程仍在持续建设 |
| 交互与执行接入 | Web 是当前交互前端，通过 SteerRunner 接入本地 Codex、本机 Orca 和远端 Orca 路径 | 各组合的可执行资格与已验范围分别确认 |

**面向用户的 SteerLine 主 Agent、贯穿完整项目周期的流程管理，以及授权范围内的有限自主推进，仍是后续产品方向。** 当前的解析、生成和执行能力尚不构成完整的主 Agent 产品体验。

长期愿景是通往工程 AGI，让 AI 能持续承担复杂软件项目的开发。项目会按阶段完善流程与工具体系，用明确的交付与验收记录检验进展。
